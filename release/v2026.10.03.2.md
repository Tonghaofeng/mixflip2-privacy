# v2026.10.03.2 — permguard：Shizuku 守门员（开机自动拉起 Shizuku）+ 远程维护隧道

## 一、一句话定位

手机重启后，不用人去点 Shizuku：PermGuard 自己把 Shizuku 和守护循环拉起来，远程维护隧道也会自动连回 Mac mini。

v2026.10.03.1 只提交、没有发版，内容一并写在这里。

## 二、改了什么

- **Shizuku 守门员**（`permguard/app/src/…/Watchdog.java`、`Adb.java`，OPEN_ITEMS #20）
  - 为什么要它：Shizuku 13.6 自带的开机启动只在开机广播那一刻试一次，Wi-Fi 没连上就放弃。
  - 怎么做：Shizuku 没在跑时，PermGuard 用 ADB-over-TLS 连本机 adbd（身份 shell），跑 Shizuku 的 starter，再 `pg.sh daemon-start`。
  - 何时跑：`LOCKED_BOOT_COMPLETED` 起，未解锁也跑；另外 Wi-Fi 连上、binder 断开、每 30 分钟兜底时也会跑。
  - 失败了就退避重试；连续两轮失败发通知。
  - adb 钥匙由新增的 `permguard/adb/pair_watchdog.sh` 一次性配好，全程不碰手机。
  - 设计见 `permguard/README.md`「Shizuku 守门员」。
- **远程维护隧道 `permguard/remote/`**（.1 起）
  - 链路：手机 shell 身份的 dropbear dbclient 反向转发无线调试端口 → Mac mini `127.0.0.1:15556`。
  - 由守护循环的 `hooks.sh` 保活，不依赖 Termux。
- **rt.sh 远端口轮换**：15556 被 Mac 上的旧会话占着时，依次换 15557、15558。
  - 修正了 AIOS 版的检测：手机 toybox grep（BRE）不认 `\|`，原检测永远不生效；dbclient 转发失败也不退出。
  - 现在整个连接期间都用单一模式检测。
- **守门员计数 bug**
  - 问题：「同一次连接最多试 3 次」按网络句柄计数，但句柄跨重启重复，计数从不清零，所以第 3 次开机就不再开无线调试。
  - 修复：改为按「开机次数:句柄」计数，开成功就清零。
- `pg.sh` 守护循环每轮调用可选的 `hooks.sh`；`setup_phone.sh` 遇到已装的包就跳过重装（`PG_REINSTALL=1` 强制重装）。

## 三、结果（实测）

两次经隧道 `adb reboot`，手机在外（Wi-Fi + Clash），开机后只输一次 PIN（证据 `evidence/permguard_20261003/reboot_watchdog.md`）：

| | 解锁 | Shizuku 就绪 | 守护 + GuardJob 补跑 | 隧道恢复 |
|---|---|---|---|---|
| 第 1 次 22:53 | +22s | +34s（守门员拉起） | +35s，apply rc=0 | +6m00s（旧检测 bug） |
| 第 2 次 23:09 | +22s | +25s（Shizuku 自启抢先，守门员开了无线调试） | +26s，apply rc=0 | **+29s** |

- 两次 dropbox 都是 0 崩溃。
- 端口轮换在线实测：从判定 15556 被占到 15557 连上，约 30 秒。
- 本版 APK（versionCode 20261006）23:13 已装到手机。装完后守门员 `ok:binder`，守护循环在跑，classpath 已指向新 APK。
- **还没在本版 APK 上做过重启验证**：上面两次重启跑的是 versionCode 20261005，只差计数修复。

## 四、仍保留与理由

- **Mac mini sshd 没开 ClientAliveInterval**：改要 sudo，所以用端口轮换绕开旧会话。
- **公网对 22 端口的爆破**：会让 sshd（MaxStartups）偶尔丢掉手机的连接，rt.sh 20 秒后重试。根治要 sudo 改 sshd，或收窄 22 端口的暴露面。
- **隧道要等解锁之后才能连上**：Clash 是 always-on VPN。

